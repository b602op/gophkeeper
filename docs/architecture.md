# Архитектура GophKeeper

Документ описывает компоненты системы, слои, потоки данных и ключевые
технические решения.

## Общая схема

```
┌──────────────────────────────┐        HTTPS/HTTP         ┌──────────────────────────────┐
│         CLI-клиент           │  Authorization: Bearer    │            Сервер            │
│                              │ ────────────────────────► │                              │
│  internal/cli  (cobra)       │                           │  internal/handler/http       │
│  internal/api  (HTTP-клиент) │ ◄──────────────────────── │  internal/middleware         │
│  internal/session (токен,    │        JSON + JWT         │  internal/service            │
│                    ключ)     │                           │  internal/repository         │
│  internal/crypto (Argon2id,  │                           │  internal/domain             │
│           AES-GCM)           │                           │                              │
│  internal/storage (BoltDB)   │                           │        PostgreSQL 16         │
└──────────────────────────────┘                           └──────────────────────────────┘
```

Клиент хранит данные локально (BoltDB) и синхронизирует их с сервером.
Шифрование выполняется только на клиенте; сервер оперирует шифротекстом.

## Слоистая архитектура

Зависимости направлены строго в одну сторону:

```
handlers (HTTP/CLI) -> service -> repository -> domain
```

- **domain** — модели (`User`, `Secret`) и доменные ошибки. Не зависит ни от
  чего внутри проекта.
- **repository** — доступ к PostgreSQL через `pgx` (драйвер `database/sql`).
  Реализует `UserRepository` и `SecretRepository`.
- **service** — бизнес-логика: валидация, хеширование пароля, выпуск JWT,
  проверка владельца, версионирование. Зависит от интерфейсов репозиториев,
  объявленных на стороне потребителя.
- **handler/http** — тонкий слой: разбор запроса, выбор статуса, сериализация.
  Бизнес-логики не содержит.
- **middleware** — JWT-авторизация, логирование запросов, recovery.

Клиентские пакеты повторяют тот же принцип: `cli` — тонкий слой поверх
`api`, `storage`, `crypto`, `session`; зависимости внедряются через структуру
`app`, что делает команды тестируемыми без реального сервера.

## Потоки данных

### Регистрация

1. `register --login alice --password ...` → `POST /api/v1/register`.
2. Сервер валидирует данные, хеширует пароль bcrypt и сохраняет пользователя.
3. Клиент сразу выполняет `POST /api/v1/login` и сохраняет JWT в файл токена
   (права `600`).

### Вход

1. `login --login alice --password ...` → `POST /api/v1/login` → JWT.
2. Клиент сохраняет токен.
3. Определяется соль KDF: из кэша сессии, из локальных секретов, с сервера или
   генерируется новая.
4. Клиент запрашивает мастер-пароль, выводит ключ Argon2id и кэширует его в
   памяти процесса (TTL 5 минут). Мастер-пароль на сервер не уходит.

### Добавление секрета

1. `add` собирает открытые данные из флагов или интерактивно.
2. Данные сериализуются в JSON и шифруются ключом AES-256-GCM.
3. К шифротексту добавляется соль KDF (см. ниже) и base64-шифротекст.
4. `POST /api/v1/secrets` — сервер присваивает `id`, `version = 1` и сохраняет.
5. Ответ сохраняется в локальную BoltDB.

### Синхронизация

Стратегия — **Incremental Sync Strategy: Priority on Consistency of Deletions**:
приоритет отдаётся согласованности удалений, а создание и обновление работают в
режиме **pull-only** (источник истины — сервер).

1. Клиент читает `last_sync` из локальной базы.
2. `GET /api/v1/sync?since=<last_sync>` — сервер возвращает изменения, включая
   удаления (tombstone, `deleted_at != nil`), и `sync_watermark` — серверное
   «сейчас».
3. Серверные записи применяются локально идемпотентно (`SaveFromServer`):
   запись сохраняется, только если её версия больше локальной, иначе
   пропускается. Tombstone-записи удаляются из BoltDB.
4. Локальные записи, изменённые после `last_sync`, пытается отправить
   `pushLocalChanges` (`internal/cli/sync.go`) через `PUT`. На практике это
   no-op: отслеживания «грязных» записей нет, а локальные правки в обход сервера
   не возникают.
5. При конфликте версий при обновлении выполняется интерактивное разрешение.
6. `last_sync` обновляется значением `sync_watermark` из ответа сервера, а не
   локальными часами.

Ограничения: при одновременном удалении и обновлении секрета на разных
устройствах возможна потеря локального изменения; конфликты версий при удалении
не обрабатываются.

## Zero-knowledge шифрование

```
мастер-пароль ──Argon2id(соль)──► мастер-ключ (32 байта)
                                      │
открытые данные ──AES-256-GCM─────────┴──► "v1:<nonce>:<ciphertext>"
```

- **KDF Argon2id**: time=3, memory=64 МиБ, threads=4, keyLen=32. Защищает от
  перебора мастер-пароля.
- **Соль** (16 байт) генерируется случайно. Она хранится в поле `data` перед
  шифротекстом: `salt(16) || "v1:<base64-nonce>:<base64-ciphertext>"`. Так ключ
  можно восстановить на другом устройстве: соль берётся из любой существующей
  записи (локально или с сервера), а не только из памяти.
- **AES-256-GCM**: nonce (12 байт) случаен для каждой записи; префикс `v1`
  позволяет менять схему без потери совместимости.
- Мастер-ключ живёт только в памяти процесса (TTL 5 минут) и не сохраняется на
  диск. При `logout` он затирается, файл токена удаляется.

Сервер не имеет доступа к мастер-паролю и ключу, поэтому даже при компрометации
базы злоумышленник получит только шифротекст.

## Оптимистичная блокировка и конфликты

Каждый секрет имеет `version`. Обновление выполняется в транзакции:

1. Читается текущая версия записи.
2. Если она не совпадает с версией в запросе — возвращается
   `ErrSecretVersionMismatch` (HTTP `409`).
3. Иначе запись обновляется, `version` увеличивается, `updated_at` обновляется;
   новые значения возвращаются клиенту через `RETURNING`.

При конфликте клиент показывает локальную и серверную версии и предлагает выбор:

- `[l]ocal` — перезаписать серверную версию локальной (повторный `PUT` с
  актуальной серверной `version`);
- `[r]emote` — принять серверную версию в локальную базу;
- `[s]kip` — пропустить запись.

Мягкое удаление (`deleted_at`) и увеличение `version` при удалении позволяют
распространять удаления между клиентами через `sync`. Конфликты версий при
удалении не разрешаются: `DELETE` не принимает `version`, поэтому при
одновременном обновлении и удалении одной записи на разных устройствах
локальное изменение может быть потеряно.

## Выбор хранилищ

| Хранилище | Сторона | Почему |
| --- | --- | --- |
| PostgreSQL | сервер | транзакции, конкурентный доступ, надёжность, BYTEA для шифротекста |
| BoltDB | клиент | embedded, без CGO, кроссплатформенность, простые транзакции |

Локальная база разделена по пользователям:
`~/.local/share/gophkeeper/<user_id>/secrets.db`. Данные разных пользователей
не смешиваются. Файл токена и каталоги создаются с ограниченными правами
(`600`/`700`).

## Конфигурация и запуск сервера

Сервер собирает конфигурацию из четырёх источников с приоритетом
**флаги > env > JSON-файл > дефолты** и валидирует её до старта (fail early):
пустой секрет JWT, битый DSN или некорректный адрес останавливают запуск.

При старте сервер открывает пул соединений с PostgreSQL, собирает сервисы и
хендлеры, оборачивает маршруты middleware и запускает HTTP-сервер. По
`SIGINT`/`SIGTERM`/`SIGQUIT` выполняется graceful shutdown с таймаутом.

## Миграции

Миграции хранятся в `internal/repository/migrations` и применяются через goose:

- `00001_create_users.sql` — таблица пользователей;
- `00002_create_secrets.sql` — таблица секретов (UUID, BYTEA, version,
  deleted_at).
